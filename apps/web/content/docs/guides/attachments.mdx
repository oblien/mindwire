title: Attachments
description: Send files, images, and audio through durable uploads or host paths.
---

A turn can carry **attachments**: files, images, or audio sent alongside your message. You pass
them the same way for every agent; the adapter maps them to whatever that agent's CLI expects.

**Images are true vision input.** When an attachment is an image, the model actually *sees* the pixels —
it doesn't just receive a file path it has to open with a Read tool. Codex feeds images to
`localImage` input through Codex app-server (or `-i` in exec mode); Claude delivers them as base64 image content blocks over a stream-json
turn. Other files are referenced by path (the model opens them with its own tools), with native audio
available for supported Codex models as described below. The
`imageInput` [capability](/docs/guides/agents) flag reports whether an agent sees images natively — both
Claude and Codex do.

For mobile, browser, and remote clients, upload once and send the returned reference. Uploads use the
same authenticated connection as chat, with replayable 384 KiB chunks and a full-file SHA-256 check.
Files remain with the conversation after the turn ends and travel with project context switching.
There is no background synchronization or polling while idle.

```ts
const attachment = await mw.uploadAttachment("demo", {
  name: "design.png",
  mime: "image/png",
  data: new Uint8Array(await file.arrayBuffer()),
}, { onProgress: fraction => console.log(Math.round(fraction * 100)) });

const run = await mw.turn({
  chatId: "demo",
  message: "Implement this design",
  options: { attachments: [attachment] },
});
```

The Go equivalent is `client.UploadAttachment(chatID, name, mime, data)`. REST clients send chunks to
`PUT /chats/{id}/attachments/{attachmentID}` with `name`, `mime`, `bytes`, `sha256`, `offset`, and base64
`data`, then send `{ artifactId: attachmentID }` in `options.attachments`. Keep the same upload ID when
retrying; the response reports the next confirmed `offset` and `complete`. Uploaded files are limited
to 16 MiB each, eight attachments per turn, and 512 MiB of artifact storage per workspace.

`GET /artifacts/{id}` loads an attachment on demand. History carries references instead of copying
large file bytes into every message page. Deleting the last conversation that uses an attachment
removes its saved file; inherited attachments remain available in conversation forks.
`attachmentUploadVersion: 1` in health advertises this protocol; older services still accept small
inline images but must be updated for durable file uploads.

## Voice and audio

The composer microphone first shows [native harness voice](/docs/guides/voice). **Record an audio
file** is a separate option and records mono AAC in an M4A file. Stop to review the waveform, listen back, add
an optional caption, or record again. **Audio is the default:** stopping does not transcribe or send
anything. Add it to the composer, then send it through the same attachment upload and turn queue as
other files. Recordings stop on backgrounding or microphone interruption and remain available for
review. The recording limit is ten minutes.

Codex's `audioInput` capability means its app-server accepts native audio. Mindwire also checks the
selected model's `inputModalities` on that same connection, only when an audio input arrives. A model
that advertises `audio` receives `localAudio`, including mid-turn steering. Other models, Claude, and
adapters without this capability receive the unchanged recording as a readable file. They need an
audio tool to interpret it; attaching a file alone does not add audio understanding to a text-only
model. Mindwire never switches the model or silently transcribes the recording.

Use the same `uploadAttachment` API with a name such as `voice.m4a` and MIME `audio/mp4`. An empty
`message` is valid when there is an attachment. WAV, MP3, M4A, Ogg/Opus, FLAC, AAC, and WebM audio are
recognized for Codex's native route; other formats remain ordinary files. Durable audio references
survive reconnecting, queued turns, history reloads, and conversation forks.

**Add transcription** is a separate, optional action in the recording sheet. It uses on-device iOS
speech processing, downloading the chosen language's system assets if needed. The original recording
stays selected, and failure or cancellation leaves it available. Nothing is sent to a transcription
service. You can edit the text or choose to send only the text before adding it to the composer.

## Attachment fields

An attachment has one source: an uploaded **artifact reference**, a **path** on the daemon host, or
**inline base64 data**. Ordinary remote files should use uploads so they remain available on resume.

| Field | Type | Meaning |
| --- | --- | --- |
| `artifactId` | string | Durable reference returned by `uploadAttachment`. The daemon resolves its saved name, MIME, and path. |
| `path` | string | A path readable by the daemon. Use when the file already lives where the daemon runs. |
| `data` | base64 string / `[]byte` | Inline bytes. Use when the client and daemon aren't on the same host. |
| `mime` | string | Optional MIME type (e.g. `image/png`); helps the agent classify the bytes. |
| `name` | string | Optional display name. |
| `bytes` | number | File size returned by an upload, for display without downloading its data. |

Attachments ride on `options.attachments` — one array on the same `turn` call you already make.

<Tab value="TypeScript">

```ts
import { readFileSync } from "node:fs";

const run = await mw.turn({
  chatId: "demo",
  message: "What's wrong in this screenshot?",
  options: {
    attachments: [
      // By path — the daemon reads it from disk:
      { path: "/abs/path/diagram.png", mime: "image/png", name: "diagram" },
      // Or inline, base64-encoded — when the daemon can't see your filesystem:
      { data: readFileSync("./shot.png").toString("base64"), mime: "image/png" },
    ],
  },
});
```

import "os"

img, err := os.ReadFile("./shot.png")

run, err := client.Turn(ctx, mindwire.TurnRequest{
	ChatID:  "demo",
	Message: "What's wrong in this screenshot?",
	Options: mindwire.TurnOptions{

`Attachment.Data` is a `[]byte`; `encoding/json` marshals it to base64 automatically, so it matches the
`data` string the REST and TypeScript surfaces send.

## Notes

- **Path vs. data.** `path` avoids copying bytes through the API but requires the file to be readable by
  the daemon process (fine for an embedded local daemon; not for a remote one). `data` works anywhere at
  the cost of the base64 payload. Prefer `path` for a local daemon, `data` for a remote one.
- **Agent support.** Attachments map to each agent's native mechanism. Codex routes images to `-i` on the
  exec transport; Claude sends base64 image blocks over a stream-json turn. Check an agent's
  [capabilities](/docs/guides/agents) (`imageInput`) for whether images are seen natively.
- **Inline size.** Inline `data` for a Claude image is base64-encoded and delivered over the CLI's
  stdin, which caps a single message at roughly **10 MB**. For larger images prefer `path` (the daemon
  reads the file directly) or downscale before attaching. Codex reads from disk, so it isn't affected.
- Attachments are one of the per-turn [`options`](/docs/guides/configuration#per-turn-options) — they
  apply to that single turn only.
